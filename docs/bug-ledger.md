# Bug ledger

One row per bug fix, newest first. Kept in the same commit as the fix (see `CLAUDE.md`). The ledger answers "what broke, why, and how do we know it stays fixed?" in one line each. Longer investigations go in `docs/history.md`; user-visible wording goes in `CHANGELOG.md`.

Columns: **Date** · **Commit** (short hash; `pending` until committed, then fill in) · **Symptom** (what the user or a test saw) · **Root cause** · **Fix** · **Regression test** (test name or e2e script; `none` with a reason if untestable).

| 2026-10-11 | pending | On Windows, Stop on a hung hook said "Stopped committing." but the hook's own commands kept running until they ended by themselves (forever, if truly hung), and each such Stop left a background thread blocked on git's output pipe. Seen as two Stop tests taking ~60 s on Windows CI; confirmed by a diagnostic run (closed PR #13): the hook's `sleep.exe` survived Stop with a parent process that no longer existed. | Stop killed git with `taskkill /T`, which follows parent-process links. Git for Windows' shell (MSYS) emulates exec by starting a new Windows process, so a hook's commands have a parent that has already exited and `taskkill /T` never reaches them. The survivor keeps git's inherited stdout/stderr open, so tokio's blocking pipe read waits too. The existing `cancel_kills_hooks_too` test passed anyway: it checked what the hook's shell did after the command, and the shell was killed. | On Windows every git process is put in its own Job Object right after it starts (`gitr-core/src/job.rs`); everything it starts joins the job, so Stop terminates the job. `taskkill /T` remains the fallback if Windows refuses a job. Programs that explicitly ask to break away may (`JOB_OBJECT_LIMIT_BREAKAWAY_OK`), and nothing is killed when git ends normally. | `cancel_kills_what_the_hook_started` (crates/gitr-core/tests/runner.rs): the hook starts `sh -c 'sleep 2; echo survived …'`; fails on Windows without the fix. |
