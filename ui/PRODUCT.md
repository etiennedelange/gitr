# Product

## Platform

web

The UI is React in a Tauri 2 webview, shipped as a Windows desktop app (NSIS installer). Design language follows Windows desktop conventions, not a website's.

## Users

Developers who work across many Git repositories at once, often in organisations that host code on both Azure DevOps and GitHub. Their day starts with "where does everything stand?" (which repos are behind, ahead, dirty or broken) and continues with the everyday loop in one repo at a time: stage, diff, commit, push, review history, switch branches. Gitr is built to be distributed to these developers and their teams, not only used by its author.

## Product Purpose

Gitr makes the state of every repository visible in one place and keeps the daily single-repo flow fast and safe. Success is a developer who can see their whole workspace at a glance, bring it up to date in one action, and do routine commits without fear of losing work or reaching for a terminal.

## Positioning

Four claims, held together:

- **Many repositories at once.** The dashboard of every repository (branch, ahead/behind, changes, errors, in-progress operations), with Fetch all and Pull all in parallel, is the core. Single-repo work is the second flow, not the first.
- **Safe by construction.** Nothing a user does in Gitr loses work: discard goes to the Recycle Bin, reset keeps changes and never goes hard, Gitr never force-pushes, Undo is offered where it can be, and confirmations state the facts of what will happen.
- **Fast and light.** Tauri and Rust instead of Electron; starts quickly, stays idle while the window is in the background, refreshes only what changed.
- **Feels native to Windows.** Behaves like a Windows app: theme and title bar follow the OS, keyboard conventions such as F6 pane cycling and Ctrl+P, Explorer-like lists, Recycle Bin, Git Credential Manager.

## Operating Context

- Open all day beside an editor (VS Code) and a terminal; Gitr hands off to both ("Open in VS Code", "Open terminal here").
- Repositories are found by pointing at root folders ("workspace groups"); repos are discovered automatically and grouped in the sidebar.
- Remotes are Azure DevOps and GitHub; links open the repo, branch, commit or a new pull request there.
- Sign-in goes through Git Credential Manager and SSH; Gitr batches sign-in so bulk fetches don't open a pile of windows.
- Commit messages can be generated by GitHub Copilot (Copilot CLI) and streamed into the commit box.
- Git hooks, rebases, merges, cherry-picks, reverts, bisects and `git am` are real states the UI must show and let the user continue, skip or abort.

## Capabilities and Constraints

- Surfaces: Dashboard (all repositories, status bar tally), repo view with Changes, History and Branches tabs, Settings, sidebar of groups and repositories, Go to repository (Ctrl+P), toasts, banners, dialogs, hook output panel.
- Operations: fetch/pull all (fast-forward only), stage/unstage/discard, unified or split diff, commit/amend/push, undo last commit, revert, reset to a commit (soft/mixed only), checkout/create/delete branch, diverged-pull rebase or merge, continue/skip/abort in-progress operations, stop a running operation.
- Requires Git 2.27+ on the machine; Gitr finds it or explains how to install it.
- Must stay usable down to the 900×600 minimum window; below 1100px the sidebar collapses to a strip.
- Light and dark themes, following Windows by default.
- Terminology: "repository", "workspace group", "changes", "behind / ahead", "Fetch all / Pull all", "Sign-in needed".
- Undecided: whether platforms other than Windows will ever ship.

## Product Principles

1. **Overview first.** Every design decision should keep the state of all repositories legible at a glance; a repo's state is never hidden behind a click.
2. **Never lose work.** Destructive-sounding actions are recoverable, and when they are not, the user is told exactly what will happen before it does.
3. **Say what git is doing.** Busy, blocked, in-progress and failed states are always visible and named, with the obvious next step offered, so the user doesn't need a terminal to understand their repo.
4. **Stay out of the way.** Fast to open, quiet in the background, operable from the keyboard, consistent with how Windows apps behave.
